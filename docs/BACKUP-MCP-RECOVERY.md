# 백업용 MCP 연결 복구

2026-11-08 점검에서 Windows 예약 백업의 Supabase MCP OAuth 토큰 갱신 실패를 확인했습니다. 웹·DB·로그인 점검은 통과했지만 새 전체 백업이 만들어지지 않아, 마지막 검증 후 48시간이 지나 `BACKUP_STALE`로 GitHub 점검이 반복 실패했습니다.

백업 도구는 공급자의 원문 오류나 인증 정보를 출력하지 않습니다. OAuth 토큰 갱신·만료·로그인 실패는 `MCP_AUTH_REQUIRED`, 일반 RPC 실패는 `MCP_REQUEST_FAILED`, MCP 도구가 반환한 실패는 `MCP_TOOL_FAILED`로 구분합니다. 초기 연결 실패도 실제 오류 분류를 유지합니다. 오류 응답이나 결과가 누락된 응답을 성공한 SQL 실행으로 간주하지 않습니다.

## 복구 순서

1. 예약 작업과 같은 Windows 사용자로 Codex의 기존 `supabase` 연결을 확인합니다. 대상은 `rbtqtkjnqtcnljvabisa` 프로젝트입니다. 서버 설정·기능·권한을 넓히지 않고 기존 OAuth 인증을 갱신합니다. CLI를 사용한다면 `codex mcp login supabase`를 실행한 터미널을 인증 완료까지 열어 두며, 로그인·콜백은 같은 PC에서 완료합니다. 비밀번호·인증 코드·토큰은 채팅이나 로그에 넣지 않습니다.
2. Windows 예약 작업은 15분마다 실행 여부를 판단하고 매시간 실제 MCP 프로젝트 URL을 확인합니다. 인증 만료는 30분 간격, 일시 연결 실패는 15·30·60분 간격으로 재시도합니다. 인증이 복구되면 누락된 전체 백업을 실행합니다. 즉시 새 백업을 요청하려면 `node scripts/operator-request-backup.mjs`를 실행합니다. 같은 예약 작업이 요청을 한 번 처리하며, 실패한 요청은 24시간 동안 재시도 대상으로 남습니다.
3. 예약 작업의 종료 코드 `0`, `agent-state.json`의 `completed`와 최신 `lastVerifiedAt`, 새 `.bfbak.verification.json`을 확인합니다. 단순 연결 점검이나 건너뛴 작업의 종료 코드만으로 새 백업을 만들었다고 판단하지 않습니다. 백업 도구는 암호문을 다시 읽어 별도 PGlite에서 데이터·외래키·접근 정책·최신 개인정보 상태를 복원 검증합니다. 운영 DB를 과거 데이터로 덮어쓰지 않습니다.
4. `/api/backup-health`가 새 검증 시각과 `healthy: true`, `code: OK`를 반환하는지 확인한 뒤 GitHub `Bookforest availability`를 재실행합니다. 서비스와 백업 검사가 모두 통과하고 기존 백업 알림 이슈가 자동 종료돼야 복구 완료입니다.
5. 기존 암호화 복구 폴더를 최신 백업과 `privacy-current.bfguard`로 갱신합니다. 복구 암호·키를 유지하며, 외부 장치 복사와 다른 실물 PC의 복구는 별도로 확인합니다.

## 인증과 독립된 장애 보고

`node scripts/operator-setup-agent.mjs`로 이 운영자 PC를 한 번 등록한 뒤 `powershell -NoProfile -File scripts/Install-Operator-Backup.ps1`로 예약 작업을 설치합니다. 전용 HMAC-SHA256 키는 운영자 전용 폴더에 AES-GCM으로 암호화하고 Windows DPAPI로 보호합니다. 이 키는 제한된 상태 보고만 서명하며, 자료 조회·백업 성공 기록 생성·계정 작업 권한은 없습니다. 서비스 역할 키를 사용하지 않습니다.

MCP의 OAuth 갱신 실패와 공식 `reauthenticationRequired` 신호를 구분하고, OAuth와 독립된 Supabase Data API 경로로 서명한 상태를 전송합니다. 서버는 서명·시간 범위·증가 순번·재전송 일치 여부를 검사합니다. 인증 복구나 `completed` 상태 보고만으로 알림을 닫을 수 없으며, 장애 이후 실제 백업 복원 검증 기록이 있어야 정상으로 돌아갑니다. 상태 보고 경로도 실패하면 로컬에 미전송 상태를 남기고 15분 후 재시도합니다. 인터넷 전체 장애 중에는 즉시 전송할 수 없으며 기존 48시간 백업 신선도 검사가 계속 적용됩니다.

GitHub는 예약된 독립 점검에서 장애별 조치를 안내하는 이슈 한 개를 유지하며, 조치가 필요한 원인이 바뀔 때만 추가 댓글을 남깁니다. 정상 검증 후 복구 댓글과 함께 닫습니다. GitHub 자체 실행 지연이나 계정 알림 수신 설정까지 보장하지는 않습니다. PC가 꺼져 있거나 Windows 사용자가 로그아웃한 동안에는 이 PC의 백업이 실행되지 않으며, 로그인 후 누락분을 처리합니다.

원격 DB와 통신할 수 없었던 상세 백업 실행 내역은 로컬에 남으며 연결이 복구된 다음 백업에서 원격 기록에 반영합니다. 인증 갱신 실패를 백그라운드에서 자동 승인하거나 알림 판정 기준을 완화하지 않습니다. 다른 PC로 이전할 때 전용 상태 보고 키는 새로 등록하고 기존 `private.backup_agents` 행을 비활성화합니다. 암호화 백업·복구 키·별도 복구 암호는 기존 절차대로 관리합니다.
