# 계정·참여·기록 운영

2026-10-30 구현. 실제 학습 기능은 `/hub`, 교사 운영 화면은 `/operations`, 본인 상태와 비밀번호 변경은 `/account`에서 이용한다. 학교에서 실제 교사 신원·보호자 동의 근거를 확인하는 절차는 화면 구현으로 대신하지 않는다.

## 담당 교사의 흐름

1. 학급을 만들고 `/operations`에서 담당 학급을 선택한다.
2. `아이디, 이름` 형식으로 최대 30명을 준비한다. 아이디는 소문자·숫자로 시작하는 4~32자이며 `_`, `-`를 허용한다. 학급 별칭을 이름으로 사용할 수 있다.
3. 발급을 실행하고 **완료한 계정 안내표**를 내려받는다. 초기 비밀번호는 브라우저 메모리에만 있고 DB·이력·로그에 저장하지 않는다. 화면을 떠나면 다시 조회할 수 없다. 분실하면 담당 교사가 재발급한다.
4. 학생은 받은 아이디로 로그인한 뒤 영문 대·소문자·숫자 포함 12자 이상의 새 비밀번호로 바꾸고 다시 로그인한다.
5. 교사는 학교에서 확인한 동의의 방법·확인일·관리번호를 제출한다. 동의서 원문·보호자 연락처·학생 글은 적지 않는다. **운영자가 근거를 확인해 승인**해야 학습 데이터를 사용할 수 있다.
6. 비밀번호 재발급은 해당 학급의 학생만 가능하다. 기존 세션을 즉시 차단하고, 새 초기 비밀번호로 로그인한 학생에게 다시 변경을 요구한다.

발급 재시도는 같은 요청·명단·비밀번호를 유지한다. 준비된 사용자 UUID와 Auth의 서버 전용 작업 표식을 비교해 이미 생성된 계정만 이어 처리한다. 작업별 임대와 계정별 직렬화가 중복 처리를 제한한다. 비밀번호를 포함한 입력은 서버 비밀키를 사용하는 HMAC으로만 요청 지문을 만들며 원문은 저장하지 않는다.

## 참여 철회와 삭제

- 학생은 `/account`에서 참여 동의를 철회할 수 있다. 이미 로그인한 세션의 학습 데이터 읽기·쓰기를 DB에서 차단하고, 다른 학생에게 게시 글을 숨긴다. 교사의 기록 관리 권한은 별도로 유지된다.
- 학생은 계정·전체 학급 기록 삭제를 요청할 수 있고, 교사는 담당 학급 기록 삭제를 요청할 수 있다.
- 운영자는 삭제 범위와 주요 건수(독서 기록·제출 글·광장 글·경제 원장)를 확인하고 승인한 다음 별도로 실행한다. 초안·제출 버전·피드백·출품/심사 사본·광장 반응·보상·구매·관련 재시도 사본도 함께 정리한다. 다른 학생과 다른 학급의 기록, 공통 미션·학급·과제는 보존한다.
- 불변 경제 원장·활동 기록은 승인한 삭제 요청의 대상·학급에만 한정된 트랜잭션에서 삭제할 수 있다. 보호 트리거를 끄지 않는다. 일반 수정·삭제는 계속 차단한다.
- 전체 계정 삭제는 기록 정리 후 Auth 계정을 제거한다. Auth API가 실패하면 계정은 정지된 상태로 남으며 운영 화면에서 이어 실행할 수 있다. 기록 정리 전에는 로그인 계정을 먼저 지우지 않는다.
- 실행 전 승인 취소가 가능하다. 계정 삭제 승인을 취소한 경우에도 기존 세션은 무효이며 다시 로그인해야 한다.
- 내려받은 파일·Google로 내보낸 파일은 이 DB 삭제 범위에 포함되지 않는다. 해당 저장 위치에서 별도로 관리한다.

보관 기간은 기본 미설정이다. 담당 교사가 학교에서 정한 30~3650일의 기간을 명시한다. 마지막 학습·피드백·거래·광장 활동을 기준으로 경과 대상을 보여 주며 자동 삭제하지 않는다. 요청 뒤 새 활동이 생기면 실행 단계에서 다시 검사해 만료 삭제를 중단한다. 이 경우 운영자가 승인을 취소하고 재검토한다.

## 운영자와 인계

운영자는 교사 역할과 별도의 비공개 레지스트리에 등록된다. 가입 metadata나 클라이언트 요청으로 운영자 권한을 얻을 수 없다. 학생으로 발급받거나 학급에 등록된 계정은 교사 권한을 신청할 수 없다. 초기 교사·운영자는 프로젝트 소유자가 확인한 계정으로 준비한다.

기존 `scripts/provision-user.ts`에 stdin JSON의 `operator: true`를 명시하면 교사 계정 생성 후 서버 전용 `bootstrap_operator`를 호출한다. 비밀번호는 명령줄 인수나 저장소 파일에 넣지 않고 stdin으로 전달한다. 도구는 `NEXT_PUBLIC_SUPABASE_URL`과 서버 전용 `SUPABASE_SECRET_KEY`를 요구한다. 기존 교사를 운영자로 지정할 때도 소유자의 신뢰된 서버 경로에서 `bootstrap_operator(user UUID)`를 호출한다. 실제 계정의 이메일·비밀번호·권한 대상은 임의로 만들거나 추측하지 않는다.

운영자는 교사 권한 신청 확인, 학급·학년 모임 인계, 계정 정지·재활성화를 처리한다. 담당 학급·모임을 모두 인계하기 전에는 교사 계정을 정지할 수 없다. 자신과 등록된 운영자는 이 화면에서 정지할 수 없다. 과거 피드백·심사 작성자는 인계로 바꾸지 않는다. 운영 이력에는 행위·처리자·대상 UUID·학급·시각만 남긴다.

## 배포와 인증 경계

1. 순서대로 DB 마이그레이션을 적용한다. 공개 학습 테이블에는 RLS와 계정 상태를 검사하는 추가 정책이 있다.
2. `supabase/functions/account-operations/index.ts`와 `_shared/account-worker.ts`를 Supabase Edge Function `account-operations`로 배포한다. SDK 버전은 고정되어 있다.
3. 함수는 Supabase가 제공하는 `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`를 사용한다. 관리자 키는 브라우저나 Next 공개 환경 변수로 전달하지 않는다. Next 서버에는 기존 URL·publishable key만 있으면 된다.
4. 이 함수는 새 publishable key와 호환되도록 플랫폼의 구형 JWT 검사 대신 **함수 내부 `auth.getUser(bearer token)` 검사**를 사용한다(`verify_jwt=false`). DB는 같은 사용자 JWT로 발급·복구 권한을 다시 검사한다. 인증 없는 호출은 401, 다른 학급 대상은 거부한다. 서비스 키는 승인된 Auth API 처리와 서비스 전용 완료 RPC에만 사용한다.
5. 정지·재발급·비밀번호 변경 시 `security_cutoff`를 기록하고 서명된 JWT의 `session_id`를 `auth.sessions`의 생성 시각과 대조한다. JWT 만료 전이라도 이전 세션은 학습 RPC·RLS를 통과하지 못한다.

Vercel 연결은 이 Supabase 함수 실행의 전제가 아니다. 교사·학생이 웹앱에 접속할 호스팅은 별도로 필요하며 현재 공개 웹 배포는 아직 수행하지 않았다. Google OAuth 실제 연결, 실제 운영자 계정 준비, 실제 동의 근거 확인, 학교 기기·수업 검증도 별도 확인 대상이다.
